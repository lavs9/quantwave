# Native Port of the 60 Candlestick Patterns

**Status:** ready to execute · **Tracker:** `quantwave-wxii` (blocked by this work)
**Goal:** remove the last runtime dependency on `talib-rs` so it can move to `[dev-dependencies]`, and make the "221 native indicators" claim literally true.

---

## 1. Why this exists

`quantwave-core` declares `talib-rs` under `[dependencies]`, so every downstream `cargo add quantwave` pulls a third-party C-lineage crate into the build graph and supply chain.

Of the 221 catalogued indicators, **60 are not native** — they are talib-rs wrappers. All 60 are candlestick patterns, generated by the `native_cdl!` macro in `quantwave-core/src/indicators/talib_wrapper.rs:67`. Despite the name, that macro is the opposite of native:

```rust
fn last_signal(o: &[f64], h: &[f64], l: &[f64], c: &[f64]) -> f64 {
    $talib_func(o, h, l, c)          // talib_rs::pattern::cdl_*  — called EVERY BAR
        .ok().and_then(|res| res.last().copied()).unwrap_or(0) as f64
}
```

Each `next()` pushes onto a 32-bar window and re-runs the full talib **batch** function, discarding all but the last value. So the port buys three things at once:

1. **Dependency removal** — the only remaining runtime `talib_rs` calls in library code.
2. **Correct claim** — 221 native indicators becomes true.
3. **Performance** — O(window) work per bar collapses to O(1).

### What is already native (do not touch)

Verified by inspection — these macros take plain closures, not talib functions:

| Macro | Count | Status |
|---|---|---|
| `native_pointwise_1!` | 15 | Native (`f64::acos`, `f64::ceil`, …) |
| `native_binary_2!` | 4 | Native |
| `native_cdl!` | **60** | **talib-backed — this port** |

The other 11 `talib_*` macros in `talib_wrapper.rs` (`talib_cdl!`, `talib_1_in_1_out!`, `talib_2_in_1_out!`, …) have **zero invocations**. They are dead code and should be deleted as part of this work.

## 2. Two facts that make this far smaller than it looks

### 2a. There is already a worked native example in-repo — copy its shape

`CDLDOJI` has **already been ported natively**. `quantwave-core/src/indicators/incremental/cdl_doji.rs` (89 lines) is the canonical shape for all 60:

```rust
//! Native O(1) streaming CDLDOJI (matches `talib_rs::pattern::cdl_doji`).
const LOOKBACK: usize = 10;
const FACTOR_DIV: f64 = 0.1 / LOOKBACK as f64; // 0.01

pub struct CDLDOJI {
    bar_index: usize,
    hl_sum: f64,                  // running sum
    hl_window: RingBuffer<f64>,   // fixed-capacity window
}
```

Read this file first. It already demonstrates the running-sum + ring-buffer conversion, the `bar_index` warmup gate, and the doc-comment convention recording TA-Lib as the source. **Every pattern in this port should look like this file.**

Note it folds the candle setting into two consts (`LOOKBACK`, `FACTOR_DIV`) rather than carrying a `CandleSetting` struct. That is fine for a one-setting pattern; multi-setting patterns need the shared infrastructure in §3. Keep the two approaches consistent — prefer the shared types, and consider retrofitting `cdl_doji.rs` onto them at the end.

**`RingBuffer<T>` already exists** — `quantwave-core/src/utils.rs:4`, re-exported via `indicators::incremental::utils`. Do not write a new one.

### 2b. A complete pure-Rust reference for all 60 exists locally

```
~/.cargo/registry/src/index.crates.io-*/talib-rs-0.1.2/src/pattern/mod.rs   (2194 lines)
```

This is a **batch → incremental conversion**, not a from-scratch port. Read the reference for each pattern and restructure it to hold state across bars.

It gets better: the reference is *already written in a rolling style*. TA-Lib maintains running sums that it updates in place inside the batch loop — e.g. `cdl_3linestrike` keeps `near_sum: [f64; 4]`, seeds it over the warmup, then adds the entering bar and subtracts the leaving bar each iteration. **That running-sum logic is exactly what the streaming struct needs.** Lift it out of the loop and into struct fields.

Per `AGENTS.md`, the source of every calculation must be recorded and never assumed. The recorded source for all 60 is **TA-Lib** (via `talib-rs-0.1.2`, which states it matches C TA-Lib `ta_common.c`). Cite it in each file's doc comment.

## 3. Shared infrastructure (build this first — everything depends on it)

Verified verbatim from `talib-rs-0.1.2/src/pattern/mod.rs:10-36`.

```rust
enum RangeType { RealBody, HighLow, Shadows }

struct CandleSetting { range_type: RangeType, avg_period: usize, factor: f64 }
```

| Setting | RangeType | avg_period | factor |
|---|---|---|---|
| `BODY_LONG` | RealBody | 10 | 1.0 |
| `BODY_VERY_LONG` | RealBody | 10 | 3.0 |
| `BODY_SHORT` | RealBody | 10 | 1.0 |
| `BODY_DOJI` | HighLow | 10 | 0.1 |
| `SHADOW_LONG` | RealBody | **0** | 1.0 |
| `SHADOW_VERY_LONG` | RealBody | **0** | 2.0 |
| `SHADOW_SHORT` | Shadows | 10 | 1.0 |
| `SHADOW_VERY_SHORT` | HighLow | 10 | 0.1 |
| `NEAR` | HighLow | 5 | 0.2 |
| `FAR` | HighLow | 5 | 0.6 |
| `EQUAL` | HighLow | 5 | 0.05 |

> `avg_period = 0` for the SHADOW_LONG family means **no averaging** — the range is taken from the current bar only. Handle that branch explicitly; it is a common source of off-by-one bugs.

Helpers (verbatim):

```rust
fn real_body(open, close)        -> (close - open).abs()
fn upper_shadow(open, high, close) -> high - open.max(close)
fn lower_shadow(open, low, close)  -> open.min(close) - low
fn candle_color(open, close)    -> if close >= open { 1 } else { -1 }
```

`RangeType` resolves to: `RealBody` → `real_body`, `HighLow` → `high - low`, `Shadows` → `upper_shadow + lower_shadow`.

### What to build

`quantwave-core/src/indicators/patterns/candle_settings.rs`:

- The `CandleSetting` / `RangeType` types and the 11 constants above.
- A reusable **`RollingCandleAvg`** struct built on the existing `RingBuffer<T>` (`quantwave-core/src/utils.rs:4` — do NOT write a new ring buffer), covering `avg_period` bars, O(1) `push`/`sum`, correctly handling `avg_period == 0` (no averaging, current bar only).
- A **`CandleWindow`** struct holding the last N OHLC bars in a ring buffer, with `MAX_LOOKBACK = 14` (derived below) — indexable backwards as `bar(0)` = current, `bar(1)` = previous, matching TA-Lib's `i`, `i-1`, `i-2` idiom so ported code reads like the reference.

**Window sizing:** the largest lookback across all 60 is **14** (`BODY_LONG.avg_period(10) + 4`, from `breakaway`, `mathold`, `ladderbottom`, `risefall3methods`). So a window of **15 bars** (lookback + current) suffices for every pattern. The current `MAX_WINDOW = 32` is over-provisioned; do not blindly copy it.

Port **one exemplar pattern** alongside the infrastructure to prove the shape before parallelising:
- `CDL3LINESTRIKE` — exercises multi-slot running sums (`near_sum: [f64; 4]`) and a 3-bar lookback

`CDLDOJI` is already native (§2a) and serves as the single-setting reference; `CDL3LINESTRIKE`
proves the multi-setting, multi-bar case that the shared infrastructure has to support.

## 4. Per-pattern porting recipe

For each pattern:

1. Open the reference implementation in `talib-rs-0.1.2/src/pattern/mod.rs`.
2. Identify its `let lookback = …` line (table in §5) and which `CandleSetting`s it uses.
3. Create the struct with: a `CandleWindow`, one `RollingCandleAvg` per setting used, and a `bars_seen` counter.
4. Move the batch loop's per-iteration body into `Next::next()`.
5. Move the batch's warmup seeding into the accumulation branch of `next()` (before `bars_seen > lookback`).
6. Move the batch's "add entering, subtract leaving" sum maintenance into `next()`, after emitting.
7. Return `0.0` until `bars_seen > lookback`, matching TA-Lib's zero-fill for the unstable period. **Do not return NaN** — TA-Lib patterns emit `0` (no signal), and existing callers depend on it.
8. Implement `next_batch()` if a faster bulk path is natural; otherwise the default is fine.

### Output contract — do not change it

- Return type stays `f64`, values `-100.0`, `0.0`, `+100.0` (some patterns emit `±200` — check the reference; `kickingbylength` and `risefall3methods` differ).
- The existing `native_cdl!` returns `.unwrap_or(0) as f64`. Preserve exact numeric output; these feed the `.ta` namespace and the 221-indicator metadata registry.
- Struct names stay identical (`CDLHAMMER`, `CDL2CROWS`, …) — the metadata registry, Polars plugins and Python bindings all reference them by name. **Renaming breaks the public API and the catalog.**

## 6. Verification — non-negotiable

**`talib-rs` remains available in `#[cfg(test)]` and `benches/` throughout.** It stays as the oracle; only the *runtime* dependency goes away. Do not delete the dev-dependency.

Every ported pattern needs, at minimum:

1. **Oracle parity proptest** — random OHLC series (length 1..200, and separately 1..30 to stress the warmup boundary):
   ```rust
   let native: Vec<f64> = (0..len).map(|i| s.next((o[i], h[i], l[i], c[i]))).collect();
   let oracle = talib_rs::pattern::cdl_xxx(&o, &h, &l, &c).unwrap();
   for (n, t) in native.iter().zip(oracle.iter()) {
       assert_eq!(*n, *t as f64);   // exact — these are discrete signals, not floats
   }
   ```
   Use `assert_eq!`, not approx. Pattern outputs are exactly `0`, `±100`, `±200`.

2. **Batch↔streaming parity proptest** — the workspace-wide `Next<T>` requirement.

3. **Degenerate input coverage** — proptest generators must include flat bars (`open == high == low == close`), zero ranges, and gaps. Division by a zero range is the most likely divergence, and uniform-random generators rarely produce it.

4. **Bounded memory test** — feed 100k bars, assert internal buffers stay at their fixed capacity. The pre-existing `history: Vec` leaks in KAMA and BBANDS were exactly this bug; do not reintroduce it.

Coverage is machine-checked by `scripts/check_indicator_parity_coverage.py` (currently 215/221 with 7 exemptions). **It must not regress.**

## 7. Project constraints — read before writing code

- **NEVER run `cargo fmt --all` or `cargo fmt -p <crate>`. It hangs indefinitely.** `quantwave-core/src/options_india/iv_solver.rs` contains Horner-form polynomials (~12 nested paren levels on 500-char lines) that make rustfmt spin at 100% CPU, and rustfmt follows `mod` declarations so all of `quantwave-core` becomes unformattable. **Use `./scripts/rustfmt_check.sh`** — whole workspace, ~1.2s. If rustfmt processes pile up: `pkill -f "bin/rustfmt"; pkill -f cargo-fmt`.
- **Tests:** `cargo nextest run --workspace` — nextest is mandatory, not `cargo test`.
- **Clippy:** `cargo clippy -p quantwave-core -p quantwave-polars -p quantwave-backtest --all-targets -- -D warnings`.
- **Integration tests and gold-standard files must live in `quantwave-core/tests/`.** Root-level `tests/` folders are prohibited for Rust.
- **Doc/metadata gate** — CI runs 15 scripts that local testing misses. Before finishing:
  ```bash
  for s in check_metadata_drift check_doc_drift check_public_metadata check_repo_hygiene \
           check_indicator_parity_coverage check_core_safety check_validation_docs \
           check_bead_ids check_talib_map_drift check_api_stubs_drift check_doc_links; do
    python3 scripts/$s.py || echo "FAILED: $s"
  done
  ```
  `check_validation_docs` will fail once after adding tests — regenerate with `collect_validation_stats.py && render_validation_docs.py` and re-run.
- **Never put tracker IDs (`quantwave-xxxx`) in shipped Python package files.** `check_bead_ids.py` lints for it and CI fails. Rust files are currently exempt.
- **Python verification** needs a rebuilt extension: `maturin build -m quantwave-py/Cargo.toml --release`, extract `_lib.abi3.so` from the wheel, run pytest with `PYTHONPATH` pointed at the source tree.
- **Git:** `git commit --no-verify` — legacy hooks hang. Work on a branch.

## 8. Suggested execution plan

**Phase 1 — infrastructure (sequential, one agent, must land first).**
`candle_settings.rs` + `RollingCandleAvg` + `CandleWindow` + `CDLDOJI` and `CDL3LINESTRIKE` as exemplars + the reusable parity-test macro. Everything else depends on the shape this establishes. Review it before fanning out.

**Phase 2 — the five batches (parallel, one agent each).**
Give each agent its own file (`patterns/single_bar.rs`, `two_bar_a.rs`, …) and its own git worktree, so there are no merge conflicts. Each agent registers its structs but **must not edit** `talib_wrapper.rs` or the shared infrastructure.

**Phase 3 — teardown (sequential, after all batches).**
- Delete `native_cdl!` and the 11 unused `talib_*` macros from `talib_wrapper.rs`; delete the file if nothing remains.
- Confirm zero `talib_rs` references outside `#[cfg(test)]` and `benches/`:
  ```bash
  grep -rn "talib_rs" --include="*.rs" quantwave-core/src quantwave-py/src quantwave-polars/src
  ```
  Watch for macro-argument forms (`macro!(NAME, talib_rs::path::fn)`) — a naive `talib_rs::\w+::\w+\(` regex misses them, which is how these 60 went unnoticed.
- Move `talib-rs` from `[dependencies]` to `[dev-dependencies]` in `quantwave-core/Cargo.toml`. Confirm `cargo build -p quantwave-core` succeeds and `cargo bench` still runs `talib_comparison`.
- Update the claim everywhere it appears: `README.md`, `docs/llms.txt`, `docs/comparison.md`, `docs/faq.md`, `docs/index.md`, the PyPI description in `quantwave-py/pyproject.toml`, and `docs/guides/backtest/capability_matrix.md` ("clean-room" framing).
